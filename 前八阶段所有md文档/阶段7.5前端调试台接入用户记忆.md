# 阶段7.5前端调试台接入用户记忆

本文档是阶段 7.5 的实施计划。它承接阶段 6.5 的 `agent-lab.html` 调试台和第七阶段的 MySQL 用户记忆系统。本阶段不是正式产品前端，而是把“长期记忆 / 短期记忆 / MySQL 持久化”接入现有可视化调试台，方便人工测试完整 Agent 行为。

阶段 7.5 的核心思想是：

```text
在现有 agent-lab.html 里增加记忆调试区
让用户可以查看、新增、禁用记忆
再观察记忆如何影响需求确认和 Planner 生成
```

页面入口仍然是：

```text
http://localhost:8080/agent-lab.html
```

文件位置仍然是：

```text
AgentProjectTrip/src/main/resources/static/agent-lab.html
```

## 1. 阶段 7.5 目标

完成后，调试台应该具备以下能力：

1. 页面顶部明确显示当前持久化模式是 MySQL/JDBC，而不是旧的纯内存模式。
2. 用户可以按当前 `sessionId` 查询记忆。
3. 页面可以区分显示 `LONG_TERM` 和 `SHORT_TERM` 记忆。
4. 用户可以手动新增长期记忆，例如“不住青旅”“偏好火车”。
5. 用户可以禁用某条记忆。
6. 用户确认需求表后，可以刷新记忆列表，看到系统自动写入的短期记忆。
7. 用户生成计划时，可以观察长期记忆是否影响 Planner 输出。
8. 页面原始 JSON 区能显示记忆接口响应，方便排查。
9. 不引入 React、Vue、Vite 或 npm 依赖。
10. 不改变后端记忆策略，只做前端可视化和调试入口。

阶段 7.5 暂时不做：

- 正式用户登录。
- 用户画像页。
- 记忆自动抽取 UI。
- 记忆冲突合并。
- 向量记忆搜索。
- 复杂表格组件。
- 正式移动端适配。
- 支付或订单 UI。
- 异步生成任务进度条。

## 2. 为什么需要阶段 7.5

第七阶段已经完成了后端能力：

```text
MySQL 持久化
Requirement / Plan / Version / Credit 持久化
UserMemory 模型
MemoryController
Planner 读取用户记忆摘要
确认需求表后同步短期记忆
```

但如果前端调试台不接入记忆系统，人工测试会很麻烦：

1. 需要用 Postman 或浏览器手动调用记忆接口。
2. 不容易观察长期记忆和短期记忆的区别。
3. 不容易验证“确认需求表 -> 写短期记忆”是否生效。
4. 不容易验证“保存长期记忆 -> Planner 参考偏好”是否生效。
5. 现有页面顶部仍提示“重启后数据丢失”，已经不符合 MySQL 模式。

所以阶段 7.5 的目标是把记忆系统放到调试台可见区域，让我们能像真实产品一样测试它。

## 4. 页面结构调整

阶段 7.5 建议把页面改成六个区域：

```text
1. 自然语言需求
2. 用户记忆
3. 需求表编辑
4. 规划结果
5. 自然语言修改
6. 原始 JSON
```

推荐布局：

```text
左侧：
- 自然语言需求
- 用户记忆
- 需求表编辑

右侧：
- 规划结果
- 自然语言修改
- 原始 JSON
```

原因：

- 记忆会影响需求抽取和 Planner，放在需求表之前更符合调试顺序。
- 记忆管理区不应该挤占规划结果区的阅读空间。
- 继续保持单文件静态页面，避免前端工程复杂度。


第七阶段后这句话已经不准确。阶段 7.5 应改为：

```text
开发调试模式：当前使用 MySQL/JDBC 持久化；sessionId 临时充当 userId。
```


## 6. 用户记忆区设计

### 6.1 记忆查询控件

控件：

```text
select: 作用域过滤
  - 全部
  - LONG_TERM
  - SHORT_TERM

button: 刷新记忆
```

调用接口：

```http
GET /api/v1/memories?sessionId=test-007
GET /api/v1/memories?sessionId=test-007&scope=LONG_TERM
GET /api/v1/memories?sessionId=test-007&scope=SHORT_TERM
```

成功后：

```text
state.memories = response.memories
更新 Memory Count
渲染记忆列表
原始 JSON 区展示响应
```

### 6.2 新增记忆控件

表单字段：

```text
scope: LONG_TERM / SHORT_TERM
type: PREFERENCE / CONSTRAINT / FACT / HISTORY / SYSTEM
key: 文本输入，例如 accommodationPreference
value: 文本输入，例如 不住青旅
source: USER_EXPLICIT / MANUAL / PLAN_FEEDBACK
```

第一版默认值：

```text
scope = LONG_TERM
type = PREFERENCE
key = accommodationPreference
value = 不住青旅
source = USER_EXPLICIT
```

按钮：

```text
保存记忆
不住青旅示例
偏好火车示例
避开人多示例
```

调用接口：

```http
POST /api/v1/memories
```

请求体：

```json
{
  "sessionId": "test-007",
  "scope": "LONG_TERM",
  "type": "PREFERENCE",
  "key": "accommodationPreference",
  "value": "不住青旅",
  "source": "USER_EXPLICIT"
}
```

成功后：

```text
刷新记忆列表
显示“已保存用户记忆”
```

### 6.3 记忆列表展示

每条记忆建议显示：

```text
[LONG_TERM / PREFERENCE] accommodationPreference = 不住青旅
source: USER_EXPLICIT
confidence: 1.0
memoryId: mem-...
禁用按钮
```

视觉规则：

- `LONG_TERM` 用蓝色或绿色标签。
- `SHORT_TERM` 用灰色或黄色标签。
- `PREFERENCE`、`FACT` 等用小标签即可。
- 每条记忆用简洁边框行，不做复杂卡片嵌套。

### 6.4 禁用记忆

按钮：

```text
禁用
```

调用接口：

```http
DELETE /api/v1/memories/{memoryId}
```

成功后：

```text
从当前列表中移除
或重新刷新记忆列表
原始 JSON 区展示响应
```

第一版不做二次确认弹窗，按钮文案可以写成“禁用”，避免误解为物理删除。

## 7. 与需求确认链路的联动

第七阶段后端已经实现：

```text
POST /api/v1/requirements/{requirementId}/confirm
-> userMemoryService.syncFromConfirmedRequirement(spec)
-> 写入 SHORT_TERM 记忆
```

阶段 7.5 前端应在 `confirmRequirement()` 成功后自动调用：

```javascript
await loadMemories(false);
```

这样用户确认需求表后，可以立刻看到新增的短期记忆。

示例短期记忆：

```text
[SHORT_TERM / FACT] destinations = 法国、意大利
[SHORT_TERM / FACT] budget = 1200EUR
[SHORT_TERM / FACT] travelerCount = 2
[SHORT_TERM / FACT] avoidances = 避开人多
```

## 8. 与生成链路的联动

第七阶段后端已经实现：

```text
LangGraphPlannerFacade
-> UserMemoryService.buildPromptContext()
-> TravelPlanState.userMemoryContext
-> PlanDraftNode prompt
```

阶段 7.5 前端不需要直接把记忆塞进生成请求。它只需要：

1. 确保当前 `sessionId` 正确。
2. 允许用户在生成前保存长期记忆。
3. 允许用户在生成前刷新记忆列表确认。
4. 生成后观察结果是否参考了长期偏好。

推荐人工测试：

```text
先保存 LONG_TERM:
accommodationPreference = 不住青旅
transportPreference = 偏好火车
avoidances = 避开人多

再生成：
国庆去法国和意大利玩10天，预算1200欧，不含国际机票，2个人，从上海出发
```

期望：

```text
规划中不主动推荐青旅。
交通方案倾向火车。
避峰策略更明显。
```

注意：

```text
如果本次需求表明确写“可以住青旅”，则本次需求优先，长期记忆不能覆盖。
```

## 10. API 错误处理

记忆区错误展示规则：

| 场景 | 页面提示 |
|---|---|
| MySQL 未启动 | “数据库不可用，请确认 MAMP MySQL 已启动。” |
| sessionId 为空 | 使用当前输入框 sessionId；仍为空时用 `test-007` |
| key/value 为空 | “记忆 key 和 value 不能为空。” |
| DELETE 失败 | “禁用记忆失败，请查看原始 JSON。” |
| GET 返回空列表 | “当前没有生效记忆。” |

第一版继续复用现有 `api()` 和 `renderJson()`，不单独做错误弹窗。

## 13. 验收标准

阶段 7.5 完成后必须满足：

1. `agent-lab.html` 能显示当前记忆数量。
2. 可以通过页面查询当前 session 的记忆。
3. 可以通过页面新增长期记忆。
4. 可以通过页面禁用记忆。
5. 需求表确认成功后，页面刷新能看到短期记忆。
6. 生成计划时不需要前端手动传记忆，后端会按 sessionId 读取。
7. 原始 JSON 区能显示记忆接口响应。
8. 页面文案不再说 MySQL 模式下后端重启会丢失所有数据。
9. 不引入新的前端构建依赖。
10. 后端现有 `mvn test` 继续通过。
